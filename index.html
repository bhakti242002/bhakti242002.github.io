How I work, whatever the role

The same five steps, whether the output is a dashboard, a model or a product spec.

  1. Frame it

    Pin down who the decision is for and what success looks like before writing a query.

  2. Explore it

    Profile the data, find the gaps, and fix quality at the source instead of working around it.

  3. Build small

    A dashboard, a model or a spec. Whichever answers the question fastest.

  4. Verify it

    AI can suggest. Execution plans, held-out years and honest baselines decide.

  5. Ship and measure

    Put it in front of people, then check whether it moved the metric that mattered.

Live Revenue Risk Check

Type any public company's ticker and get a live probability that its revenue declines next year, scored in real time from the company's actual SEC filings.

0.62ROC-AUC with 50% recall, where a naive "no decline" model catches zero real declines
  • Python
  • Scikit-learn
  • Random Forest
  • SEC EDGAR API
  • Vercel serverless
  • HTML, CSS, JS
Try it live View code
Problem
Predicting a company's revenue a year out is hard, and most portfolio models are judged on shuffled data that quietly leaks the future. I wanted something honest that runs on live data, not a frozen notebook.
Approach
Every request resolves the ticker to its SEC filer ID, pulls revenue, assets, liabilities and net income from data.sec.gov, and rebuilds four features: revenue scale, debt-to-assets, net margin and year-over-year growth. The model trains on 2009 to 2020 and is tested only on 2021 onward.
Result
0.62 ROC-AUC and 50% recall on 505 real company-years across 48 companies. A naive model looks 78% accurate while catching none of the declines. A leaderboard tab scores eight major companies live and ranks them by risk.
Trade-offs
48 large, well-known companies is a small, non-random sample. Missing XBRL tags are handled with missingness indicators rather than hidden, and the class balance shifted from 33% declines in training to 22% in testing.

Insight Bridge

Upload any messy spreadsheet and get a working dashboard with no setup. AI helps with labels and questions, but every number on screen is computed by code.

240xfaster, from 36s to 150ms on 10,000+ row files
  • Python
  • Flask
  • React
  • Claude API
  • Recharts

Try it live View code
Problem
Turning a spreadsheet into a dashboard usually means templates, manual chart picking, and guessing from column names.
Approach
Statistical type inference decides what each column really is: a date, a total, an average, a category, an ID or free text. AI suggests clean labels, resolves ambiguous cases and translates plain-English questions, while code computes every figure. It also flags missing values, outliers and near-duplicate records, and user corrections are always final.
Result
Validated on 8+ unrelated real-world datasets, from sales to student grades, with a 240x speedup after fixing a bottleneck. If the AI service goes down, the dashboard still works.
Trade-offs
One file at a time, capped at 20,000 rows, and question answering handles single-step lookups rather than multi-step reasoning.

AI SQL Auditor

Does AI's SQL advice actually hold up? I tested 120 of Claude's query rewrites against real Postgres execution plans instead of taking them on faith.

38%of AI rewrites measurably helped, and 20% made queries slower
  • Python
  • PostgreSQL
  • EXPLAIN ANALYZE
  • Claude API
  • Power BI
View code
Problem
AI assistants suggest SQL "optimizations" constantly. Almost nobody checks whether they're right.
Approach
A TPC-H style 8-table schema with about 80K synthetic rows, and a generator that produces 8 queries for each of 15 anti-patterns. Claude reviews each one, then both versions run under EXPLAIN ANALYZE.
Result
AI flagged an issue in 100% of queries. 38% of fixes helped, 34% changed nothing, 20% were slower and 8% failed to run. It was near-perfect on correlated subqueries and consistently harmful on OR conditions.
Trade-offs
Synthetic data keeps plans reproducible. A separate real-world dbt sample is reviewed qualitatively and kept out of the core numbers.

Customer Churn Prediction

End-to-end churn analytics on 7,000+ customers: SQL cleaning, Power BI dashboards, then a model that scores new customers by how likely they are to leave.

378customers flagged as likely future churners
  • SQL Server
  • Power BI
  • Python
  • Random Forest
  • Jupyter
View code
Problem
Why do customers leave, how much revenue walks out with them, and who is likely to leave next?
Approach
A three-layer build: SQL exploration, a NULL audit across 30+ features and a clean production table, then Power BI churn and prediction dashboards, then a Random Forest with feature importance.
Result
Month-to-month contracts, fiber optic plans, high monthly charges and tenure under 6 months were the highest-risk segments. Competitors and price were the top reasons for leaving.
So what
The prediction page breaks at-risk customers down by contract, tenure and payment method, so a retention team knows exactly where to start.

Gemini in Sheets: the missing confidence layer

Gemini in Sheets tells users to verify its output but never says when. I specified a confidence badge that fixes that without adding a model call.

3.3Mseat year-one market, sized with TAM, SAM and SOM
  • PRD
  • Wireframes
  • GTM rollout
  • North Star metric
  • Market sizing
Read the case study
Problem
A live Google AI feature asks users to double-check it, but gives no in-product signal for which answers need checking. That's a trust gap Google's own docs already admit to.
Approach
A deterministic confidence badge built from signals already in the sheet, so there's no added model call, cost or latency. Written up as a PRD with wireframes and a phased rollout.
Measuring it
A North Star paired with a counter-metric, so the feature can't be "improved" by making the badge more alarming and less accurate.
